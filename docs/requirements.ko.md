# QuickMD — Windows/macOS 우클릭 Markdown 변환 프로그램 개발 지침서

## 1. 역할 및 프로젝트 목표

너는 Windows와 macOS의 운영체제 통합, Python 애플리케이션 개발, CLI 설계, 패키징, 설치 자동화, 오픈소스 배포 경험을 갖춘 시니어 소프트웨어 엔지니어다.

Microsoft의 오픈소스 **MarkItDown**을 기반으로 Windows와 macOS에서 파일을 우클릭하여 Markdown으로 변환할 수 있는 크로스플랫폼 프로그램을 개발한다.

프로젝트명은 **QuickMD**로 한다.

참고 프로젝트:

- MarkItDown: https://github.com/microsoft/markitdown
- PyInstaller: https://github.com/pyinstaller/pyinstaller
- Microsoft Windows Shell: https://learn.microsoft.com/en-us/windows/win32/shell/
- Apple Automator: https://support.apple.com/guide/automator/
- GitHub Actions: https://docs.github.com/en/actions

개발을 시작하기 전에 공식 문서와 현재 라이브러리 버전, 운영체제별 설치 및 통합 방식을 확인한다.

오래된 API나 더 이상 권장되지 않는 구현에 의존하지 않는다.

### 핵심 목표

일반 사용자가 프로그램을 설치하고 Markdown으로 변환하기까지의 과정은 최대한 단순해야 한다.

1. Windows CMD 또는 PowerShell에서 설치 명령어를 실행한다.
2. macOS 터미널에서 설치 명령어를 실행한다.
3. 설치 과정에서 필요한 프로그램과 OS 우클릭 메뉴가 자동으로 등록된다.
4. 사용자는 PDF 등의 파일을 우클릭한다.
5. 'Markdown으로 변환' 메뉴를 누른다.
6. 원본 파일과 동일한 폴더에 Markdown 파일이 생성된다.
7. 변환 완료 또는 실패 시 운영체제 알림을 표시한다.

별도 프로그램 실행, 로그인, 클라우드 서버, API Key, Python 설치, 복잡한 환경 설정은 요구하지 않는다.

모든 문서 변환은 사용자의 컴퓨터에서 로컬로 처리한다.

**QuickMD는 GUI 중심의 데스크톱 앱이 아니다.**

OS에 자연스럽게 통합되어 필요할 때만 실행되는 경량 유틸리티로 개발한다.

- CMD 및 PowerShell 지원

### macOS

- macOS 13 이상을 초기 지원 범위로 설정

- Finder Quick Action
- Automator Workflow 또는 동등한 공식 통합 방식
- macOS 알림 기능
- 터미널 기반 설치 및 제거

### 개발 원칙

가능하면 Python 표준 라이브러리를 사용한다.

필요한 외부 패키지만 도입하고 불필요한 프레임워크는 추가하지 않는다.

Electron, React, 웹 서버, 별도 데이터베이스, 계정 시스템은 구현하지 않는다.

PyInstaller를 통해 Python 런타임과 의존성을 패키징하여 사용자 컴퓨터에 Python 설치가 필요 없도록 한다.

Windows와 macOS의 차이는 OS 어댑터로 분리하고 변환 로직은 공통으로 사용한다.

## 3. 최종 사용자 경험

### Windows

사용자가 설치 명령어를 한 번 실행하면 이후에는 우클릭으로 변환할 수 있어야 한다.

예시:

```text
문서 폴더
├── 사업계획서.pdf
├── 프로젝트설명서.docx
└── 기술문서.pptx
```

사용자가 `사업계획서.pdf`를 우클릭한다.

```text
마우스 우클릭
    │
    ├── 열기
    ├── 복사
    ├── 이름 바꾸기
    ├── Markdown으로 변환
    └── 속성
```

'Markdown으로 변환'을 선택하면 다음 파일이 생성된다.

```text
문서 폴더
├── 사업계획서.pdf
├── 사업계획서.md
├── 프로젝트설명서.docx
└── 기술문서.pptx
```

변환이 완료되면 다음과 같은 Windows 알림을 표시한다.

```text
QuickMD

Markdown 변환 완료

사업계획서.md 파일이 생성되었습니다.
```

### macOS

Finder에서 파일을 우클릭한다.

```text
마우스 우클릭
    │
    ├── 열기
    ├── 빠른 보기
    ├── 공유
    └── 빠른 동작
          └── Markdown으로 변환
```

Quick Action 실행 후 원본 파일이 위치한 폴더에 Markdown을 생성한다.

운영체제에서 허용하는 경우 완료 알림을 표시한다.

macOS의 Finder 메뉴 구조와 표시 위치는 OS 버전에 따라 다를 수 있으므로 실제 지원 버전에서 검증한다.

## 4. 설치 시스템

### 핵심 요구사항

사용자는 Python, pip, Git, 개발 도구를 사전에 설치하지 않아도 된다.

설치 명령어는 사용자에게 공개 배포 가능한 형태로 제공한다.

Windows에서는 CMD 또는 PowerShell에서, macOS에서는 터미널에서 명령어 한 줄로 설치할 수 있어야 한다.

Windows와 macOS의 구현은 서로 달라도 되지만 사용자 경험은 최대한 동일하게 유지한다.

### 4.1 Windows 설치

권장 배포 방식:

- GitHub Releases
- Windows 설치 실행 파일
- WinGet 패키지 등록

공개 배포 이후 최종 사용자 명령어 예시:

```powershell
winget install --id <실제등록된패키지ID> --exact
```

위 명령어는 실제 WinGet 패키지 등록 후에만 동작한다.

패키지 등록 전에는 GitHub Releases에서 배포하는 설치 파일을 다운로드하고 실행하는 공식 설치 스크립트를 별도로 제공한다.

설치 스크립트는 CMD와 PowerShell 중 지원하는 환경을 명시하고, 필요한 실행 경로와 명령어를 README에 안내한다.

외부에서 다운로드한 스크립트를 검증 없이 즉시 실행하는 방식을 기본값으로 사용하지 않는다.

Windows 설치 프로그램은 다음 작업을 수행한다.

1. 운영체제와 CPU 아키텍처 확인
2. 기존 QuickMD 설치 여부 확인
3. 배포 파일 무결성 검증
4. QuickMD 실행 파일 설치
5. Windows 우클릭 메뉴 등록
6. CLI 사용 경로 설정
7. 정상 설치 여부 검증
8. 설치 완료 메시지 출력

설치 경로는 기본적으로 사용자 영역을 사용한다.

관리자 권한이 필요하지 않은 구성을 우선한다.

동일한 프로그램을 여러 번 설치해도 중복 설치나 중복 메뉴 등록이 발생하지 않아야 한다.

### 4.2 macOS 설치

권장 배포 방식:

- GitHub Releases
- Homebrew Cask
- 필요하다면 별도 설치 스크립트

공개 배포 이후 최종 사용자 명령어 예시:

```bash
brew install --cask quickmd
```

Homebrew 공식 저장소에 등록되지 않은 경우 자체 Tap을 사용할 수 있다.

단, 실제 등록되지 않은 패키지명이나 Tap 경로를 이미 사용 가능한 명령어처럼 안내하지 않는다.

Homebrew가 설치되어 있지 않은 사용자도 이용할 수 있도록 GitHub Releases를 이용하는 독립 설치 경로를 제공한다.

macOS 설치 프로그램은 다음 작업을 수행한다.

1. macOS 버전 확인
2. Intel 또는 Apple Silicon 아키텍처 확인
3. 배포 파일 다운로드 및 무결성 검증
4. QuickMD 설치
5. Finder Quick Action 등록
6. CLI 실행 경로 설정
7. Finder에서 메뉴가 등록됐는지 확인
8. 설치 완료 메시지 출력

사용자별 설치를 기본으로 한다.

Apple의 보안 정책을 우회하거나 Gatekeeper를 전역적으로 비활성화하지 않는다.

일반 사용자용 정식 설치 배포는 진행하지 않고 개발 미리보기만 제공한다.

### 4.3 설치 자동화

설치 성공의 기준은 파일 다운로드가 아니라 실제 OS 통합 완료다.

설치 완료 후 다음 명령으로 상태를 점검할 수 있어야 한다.

```bash
quickmd doctor
```

검사 대상:

- 실행 파일 존재 여부
- QuickMD 버전
- OS 지원 여부
- MarkItDown 로딩 가능 여부
- OS 우클릭 메뉴 등록 여부
- 프로그램 설치 경로
- 알림 사용 가능 여부
- 테스트 파일 변환 가능 여부

이상이 있다면 원인과 해결 방법을 출력한다.

## 5. MarkItDown 변환 엔진

### 기본 기능

Microsoft MarkItDown을 파일 변환 엔진으로 사용한다.

변환 엔진을 직접 새로 구현하지 않는다.

처음 지원할 파일 형식은 다음과 같다.

- PDF
- DOCX
- PPTX
- XLSX

MarkItDown에서 해당 형식의 의존성을 선택적으로 설치한다.

추가 파일 형식은 확장 가능한 구조로 설계하되 초기 구현에 불필요한 의존성을 포함하지 않는다.

### 변환 예시

```text
report.pdf  → report.md
manual.docx → manual.md
slides.pptx → slides.md
data.xlsx   → data.md
```

### 변환 정책

1. 원본 파일은 절대 수정하지 않는다.
2. Markdown은 UTF-8로 저장한다.
3. 원본과 동일한 폴더에 저장한다.
4. 기본적으로 파일명은 유지하고 확장자만 `.md`로 변경한다.
5. 변환된 결과가 비정상적이거나 비어 있다면 무조건 성공으로 처리하지 않는다.
6. 변환 실패 시 원본과 기존 출력 파일을 보존한다.
7. 일부 파일에서 변환이 실패해도 다른 파일의 처리는 계속한다.

MarkItDown의 변환 결과는 문서 구조 보존을 목표로 하지만 원본 PDF의 시각적 레이아웃을 완전히 재현한다고 보장하지 않는다.

스캔 이미지 PDF는 별도의 OCR 모델이나 외부 AI API 없이 텍스트를 제대로 추출하지 못할 수 있다.

이러한 한계는 오류 메시지와 README에 명확히 안내한다.

초기 버전에서는 OCR을 추가하지 않는다.

### API 사용

가능하면 MarkItDown Python API를 직접 이용한다.

로컬 파일만 변환하므로 범용 `convert()`보다 입력 범위가 제한된 `convert_local()` 사용을 우선 검토한다.

실제 설치된 버전의 API 시그니처를 확인하고 구현한다.

예시:

```python
from markitdown import MarkItDown

converter = MarkItDown(enable_plugins=False)

result = converter.convert_local("document.pdf")

markdown = result.markdown
```

위 코드는 사용 방향을 나타내는 예시다.

실제 구현에서는 오류 처리, 파일 검증, 경로 검증, 출력 파일 저장, 로깅 등을 별도 모듈로 분리한다.

## 6. 파일 우클릭 메뉴 통합

### 6.1 Windows Explorer 통합

Windows Registry를 이용해 우클릭 메뉴를 등록한다.

기본 메뉴 이름:

```text
Markdown으로 변환
```

내부 명령어:

```text
quickmd shell-handler
```

단, 실제 명령은 설치된 실행 파일의 절대 경로를 사용하고 파일 경로를 안전하게 인수로 전달해야 한다.

#### Windows 11 처리

Windows 11의 최신 기본 우클릭 메뉴는 단순 레지스트리 기반 메뉴와 구현 방식이 다르다.

초기 버전에서는 클래식 컨텍스트 메뉴를 통한 실행을 허용한다.

이 경우 사용자가 '추가 옵션 표시'를 선택해야 할 수 있다.

기본 메뉴 직접 노출에 필요한 `IExplorerCommand`, 앱 패키지 ID, Sparse Package, COM 확장 구현 가능성을 조사한다.

단순한 Registry 설정만으로 Windows 11 기본 메뉴에 항상 나타난다고 가정하지 않는다.

복잡한 Shell Extension 개발이 프로젝트의 안정성을 해치면 초기 버전에서는 구현하지 않는다.

우선순위는 **정확한 변환과 안정적인 메뉴 실행**이다.

#### 지원 파일

메뉴는 QuickMD가 실제 변환할 수 있는 파일에서만 표시되도록 구성한다.

다음 상황을 처리한다.

- 파일 한 개 선택
- 파일 여러 개 선택
- 서로 다른 이름의 파일 선택
- 지원하지 않는 형식이 혼합된 선택
- 한글 파일명
- 공백이 포함된 경로
- 긴 경로
- 읽기 전용 파일
- 네트워크 및 동기화 폴더의 파일

#### 다중 파일 선택

Windows에서는 선택된 파일 전체를 변환할 수 있어야 한다.

`MultiSelectModel`의 의미를 공식 문서로 확인하고 적절히 설정한다.

단순히 `%1`만 전달하면 모든 파일이 한 번의 실행에서 전달된다고 가정하지 않는다.

Windows Shell의 실제 호출 방식을 검증하고 다음 중 안정적인 방법을 선택한다.

- OS가 제공하는 다중 선택 인수 전달
- 파일별 실행을 수집하는 공통 작업 큐
- 짧은 시간 안에 들어온 요청을 묶는 배치 집계 방식

초기 버전에서는 별도 상주 서비스가 없는 구현을 우선한다.

다중 파일 선택 시 일부만 처리되는 문제를 허용하지 않는다.

OS가 허용하는 선택 개수 제한도 테스트하고 문서화한다.

### 6.2 macOS Finder 통합

Finder의 Quick Action을 이용한다.

Quick Action 이름:

```text
Markdown으로 변환
```

설치 시 다음 위치에 사용자별 워크플로를 등록하는 방식을 우선 검토한다.

```text
~/Library/Services/
```

실제로 실행 가능한 Automator Workflow 형식으로 구현해야 한다.

단순한 빈 디렉터리나 불완전한 plist만 생성해서는 안 된다.

Quick Action은 사용자가 선택한 파일 경로를 QuickMD 실행 파일에 전달한다.

여러 파일을 선택했다면 모든 파일 경로를 배열 형태로 전달해야 한다.

파일 경로는 공백이나 한글을 포함해도 안전하게 처리한다.

Quick Action 등록 또는 활성화가 운영체제의 추가 승인이나 Finder 재시작을 요구한다면 해당 과정을 명확하게 안내한다.

설치 후 Finder에서 실제로 보이는지 검증한다.

## 7. 여러 파일 일괄 변환

다중 선택은 핵심 기능이다.

예시:

```text
선택된 파일

report1.pdf
report2.pdf
report3.pdf
manual.docx
slides.pptx
```

사용자가 한 번의 우클릭 명령으로 변환을 실행한다.

예상 결과:

```text
report1.md
report2.md
report3.md
manual.md
slides.md
```

### 처리 원칙

- 입력 파일별 변환 성공 여부를 개별 관리한다.
- 실패한 파일 하나 때문에 전체 작업을 종료하지 않는다.
- 동일 파일이 중복 전달되면 한 번만 처리한다.
- 파일별 예외를 기록한다.
- 과도한 동시 처리로 CPU나 메모리를 점유하지 않는다.
- 초기 버전은 순차 처리를 기본으로 한다.
- 필요할 경우 제한된 동시 처리 구조로 확장할 수 있게 설계한다.

변환 요청 목록과 최종 결과를 구분하는 작업 모델을 설계한다.

예시:

```python
class ConversionStatus(Enum):
    SUCCESS = "success"
    FAILED = "failed"
    SKIPPED = "skipped"
```

각 파일의 상태와 실제 결과 경로를 추적할 수 있어야 한다.

## 8. 출력 파일 저장 정책

기본 저장 위치는 원본 파일과 동일한 디렉터리다.

예시:

```text
/Users/user/Documents/report.pdf
```

변환 결과:

```text
/Users/user/Documents/report.md
```

### 파일명 충돌 방지

이미 동일한 이름의 Markdown 파일이 존재한다면 덮어쓰지 않는다.

예시:

```text
report.pdf
report.md
```

새로운 변환 결과:

```text
report (1).md
```

계속 충돌한다면 다음과 같이 생성한다.

```text
report (2).md
report (3).md
```

기존 파일을 삭제하거나 덮어쓰는 동작은 초기 버전에서 금지한다.

여러 프로세스가 동시에 동일한 파일을 변환하는 경우에도 파일명이 충돌하지 않아야 한다.

단순히 파일 존재 여부만 확인하고 저장하는 경쟁 조건을 피한다.

임시 파일과 원자적 파일 생성 또는 동등한 안전한 방식을 사용하여 불완전한 파일이 남지 않도록 구현한다.

변환 도중 프로그램이 종료되어도 기존 사용자 파일이 손상되지 않아야 한다.

## 9. 운영체제 알림 시스템

변환 완료 또는 실패 시 사용자에게 알림을 제공한다.

별도의 프로그램 창을 띄우지 않는다.

### Windows

Windows에서 권장되는 데스크톱 알림 API를 사용한다.

다음 내용을 표시한다.

단일 파일 성공:

```text
QuickMD

변환 완료

report.md 파일이 생성되었습니다.
```

여러 파일 성공:

```text
QuickMD

Markdown 변환 완료

총 5개 파일이 변환되었습니다.
```

일부 실패:

```text
QuickMD

일부 파일 변환 실패

성공 4개 / 실패 1개
```

### macOS

macOS 알림 기능을 사용한다.

정상적인 사용자 권한과 애플리케이션 ID에서 실행되도록 설계한다.

필요하다면 OS 기본 알림 API 또는 적합한 네이티브 브리지를 이용한다.

알림 권한이 없거나 운영체제가 알림을 표시하지 못하더라도 변환 자체는 정상적으로 동작해야 한다.

### 공통 요구사항

- 파일 하나를 변환하면 해당 결과를 알린다.
- 한 번의 배치 작업에서는 가능하면 요약 알림 한 번만 표시한다.
- 불필요한 중복 알림을 방지한다.
- 알림이 실패해도 변환 성공 여부에는 영향을 주지 않는다.
- 운영체제 설정으로 알림이 비활성화되어 있다면 이를 진단할 수 있도록 한다.
- CLI 직접 실행에서는 터미널에도 결과를 출력한다.

## 11. 프로젝트 아키텍처

전체 구조는 다음 개념을 따른다.

```text
Windows Explorer ─┐
                  │
macOS Finder ─────┤
                  │
Terminal / CMD ───┤
                  ▼
             QuickMD CLI
                  │
                  ▼
            Request Handler
                  │
                  ▼
            File Validator
                  │
                  ▼
           Conversion Manager
                  │
                  ▼
             MarkItDown
                  │
                  ▼
             File Writer
                  │
                  ▼
          Conversion Results
                  │
                  ▼
          OS Notification
```

### 주요 구성 요소

**CLI Layer**

사용자 명령, 파일 경로, 옵션을 처리한다.

**Platform Integration Layer**

Windows Explorer와 macOS Finder의 기능을 분리한다.

**Conversion Layer**

MarkItDown을 호출하고 변환 결과를 반환한다.

**File Management Layer**

입력 검증, 출력 경로 결정, 파일명 중복 처리, 안전한 저장을 담당한다.

**Notification Layer**

운영체제 알림을 담당한다.

**Installer Layer**

설치, 업데이트, 우클릭 메뉴 등록 및 제거를 담당한다.

**Diagnostic Layer**

설치 상태, 환경, 의존성, 통합 상태를 검사한다.

각 모듈은 독립적으로 테스트할 수 있어야 한다.

순환 참조를 피하고 운영체제 API와 공통 비즈니스 로직을 분리한다.

## 13. 보안 요구사항

이 프로그램은 사용자의 로컬 문서를 다루므로 보안을 중요하게 고려한다.

### 기본 보안 정책

1. 사용자가 선택한 로컬 파일만 처리한다.
2. 변환 목적으로 외부 서버에 문서를 업로드하지 않는다.
3. API Key를 요구하지 않는다.
4. 파일 경로를 셸 명령어 문자열에 직접 연결하지 않는다.
5. 가능한 경우 인수 배열을 이용해 안전하게 프로세스를 실행한다.
6. 모든 파일 경로를 검증한다.
7. MarkItDown 플러그인은 기본적으로 비활성화한다.
8. 외부 URL 변환은 지원하지 않는다.
9. 원본 파일을 수정하지 않는다.
10. 관리자 권한 실행을 기본으로 사용하지 않는다.

### 프로세스 실행 보안

Windows에서는 `shell=True` 사용을 피한다.

macOS에서는 사용자 파일명을 셸 코드에 직접 삽입하지 않는다.

공백, 따옴표, 특수문자, 줄바꿈이 포함된 파일명도 정상적으로 처리해야 한다.

신뢰하지 않는 파일로 인한 메모리 및 CPU 자원 고갈을 줄이도록 파일 크기, 변환 시간, 동시 작업 수 제한을 설계한다.

### 설치 보안

- 공식 GitHub Releases에서 배포 파일을 다운로드한다.
- 배포 아티팩트의 SHA-256 체크섬을 생성한다.
- SHA-256 체크섬으로 파일 무결성을 확인한다.
- 체크섬 파일과 실행 파일을 같은 비신뢰 경로에서 받아 비교하는 것만으로 진위가 보장된다고 가정하지 않는다.
- 릴리스 버전과 패키지 의존성 버전을 고정하거나 관리한다.
- HTTPS를 사용한다.
- 보안 경고를 우회하거나 비활성화하지 않는다.
- 설치 스크립트는 사용자 영역 외의 파일을 임의로 수정하지 않는다.

### 개인정보 보호

사용자 문서의 내용을 별도 로그에 저장하지 않는다.

진단 로그에는 필요한 정보만 기록한다.

문서 내용, API 인증정보, 민감한 파일 경로가 로그나 오류 보고를 통해 노출되지 않도록 주의한다.

## 14. 로깅 및 진단

운영체제별 적절한 사용자 데이터 디렉터리에 로그를 저장한다.

로그에 포함할 항목:

- QuickMD 버전
- 운영체제
- 변환 시작 및 종료 시간
- 지원 형식
- 변환 성공 여부
- 오류 유형
- 변환 소요 시간

로그에는 기본적으로 문서 내용을 저장하지 않는다.

로그는 무제한 누적되지 않도록 크기 및 보존 정책을 적용한다.

CLI에서 진단할 수 있도록 한다.

```bash
quickmd doctor
```

문제 발생 시 사용자에게 유용한 해결 방법을 출력한다.

예시:

```text
QuickMD Diagnostics

OS: Windows 11
Executable: OK
MarkItDown: OK
Context Menu: FAILED
Notification: OK

Suggested action:
quickmd repair
```

## 15. 프로그램 제거 및 업데이트

### 제거

Windows와 macOS 모두 제거 방법을 제공한다.

제거 시 다음 작업을 수행한다.

1. 설치된 QuickMD 실행 파일 제거
2. 운영체제 우클릭 메뉴 제거
3. 관련 설치 등록 정보 제거
4. Quick Action 또는 Registry 항목 제거
5. PATH 또는 CLI 연결 정리
6. 제거 완료 확인

사용자가 기존에 변환한 Markdown 파일은 삭제하지 않는다.

다른 프로그램의 설정이나 레지스트리 항목에 영향을 주지 않는다.

개인 로그는 정책에 따라 보존 또는 삭제를 선택할 수 있도록 한다.

### 업데이트

업데이트는 기존 설정을 유지해야 한다.

동일 버전 재설치 시 중복 등록이 발생하지 않아야 한다.

이전 버전에서 새 버전으로 업데이트했을 때 우클릭 메뉴 경로가 깨지지 않아야 한다.

프로그램을 제거하지 않고 업데이트할 수 있어야 한다.

초기 버전에서는 백그라운드 자동 업데이트를 구현하지 않는다.

패키지 관리자 또는 공식 설치 프로그램을 통한 업데이트를 지원한다.

## 16. 빌드 및 패키징

### PyInstaller

Python 코드와 런타임, 필요한 MarkItDown 의존성을 묶는다.

사용자가 별도로 Python이나 pip를 설치하지 않아도 실행되어야 한다.

Windows와 macOS는 각각의 운영체제 환경에서 빌드한다.

OS별 PyInstaller 빌드를 단순 크로스 컴파일로 처리하지 않는다.

### Windows

최종 배포 아티팩트 예시:

```text
QuickMD-Setup-Windows-x64.exe
```

Inno Setup을 이용해 설치 프로그램을 생성한다.

최종적으로 WinGet을 통한 설치를 지원하도록 매니페스트 및 등록 절차를 준비한다.

### macOS

최종 배포 아티팩트 예시:

```text
QuickMD-macOS-arm64.dmg
QuickMD-macOS-x64.dmg
```

사용자에게 별도의 앱을 실행할 필요는 없지만 실행 환경 및 알림에 필요한 경우 최소한의 앱 번들을 포함할 수 있다.

PyInstaller의 macOS 번들 권장 방식을 확인한다.

추가 자격 정보 없이 개발용 아티팩트를 생성하고, 운영체제 보안 경고가 나타날 수 있음을 분명하게 기록한다.

### 의존성

버전은 실제로 테스트한 조합을 기준으로 고정한다.

MarkItDown을 비롯한 종속 라이브러리의 라이선스와 재배포 조건을 확인한다.

불필요한 이미지 분석 모델, 클라우드 SDK, OCR 모델은 기본 패키지에서 제외한다.

## 19. 성능 및 안정성

- 일부 파일 실패 시 나머지 변환을 계속한다.
- 프로그램 충돌 후 불필요한 임시 파일이 남지 않도록 한다.
- 파일 쓰기 도중 실패해도 기존 파일은 보존한다.

- 제거 시 메뉴 등록이 함께 삭제된다.

### macOS

- Python이 없는 macOS에서도 설치할 수 있다.

## 25. Codex 작업 지침

이 프로젝트는 기획서만 작성하는 작업이 아니다.

**실제 실행 가능한 소스코드와 설치 프로그램, 빌드 스크립트, 테스트를 구현하는 것이 목표다.**

작업을 시작하면 다음 규칙을 따른다.

1. 현재 저장소를 확인한다.
2. 기존 프로젝트가 있다면 현재 구조와 코드를 먼저 분석한다.
3. 빈 저장소라면 합리적인 프로젝트 구조를 설계한다.
4. 주요 기술의 최신 공식 문서를 확인한다.
5. 요구사항을 구현 가능한 작업 단위로 나눈다.
6. 공통 변환 엔진부터 개발한다.
7. 운영체제별 통합 기능을 구현한다.
8. 테스트와 빌드 검증을 수행한다.
9. README와 배포 문서를 작성한다.
10. 구현 결과와 남은 제한 사항을 정리한다.

개발 환경에서 Windows 또는 macOS를 직접 실행할 수 없다면 해당 OS의 설치와 우클릭 테스트를 성공했다고 주장하지 않는다.

가능한 코드 구현과 자동 테스트까지 완료하고, 실제 OS에서 확인해야 하는 항목을 구분한다.

GitHub Actions 실행 권한이 없으면 해당 환경에서 수행할 수 있는 검증까지만 진행한다.

실행되지 않는 가짜 설치 파일이나 빈 함수로 기능을 구현한 것처럼 처리하지 않는다.

문제가 발생하면 가능한 범위에서 원인을 조사하고 수정한다.

특정 환경에서 해결할 수 없는 문제라면 그 제약과 추가 검증 방법을 명확히 기록한다.
